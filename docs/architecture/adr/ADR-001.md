# ADR-001. Выбор архитектурного стиля

## Статус
Принято

## Контекст
Проект «Business Metrics Analyzer» разрабатывается командой из 4 человек в сжатые сроки (учебный MVP).
Ключевые драйверы: быстрый MVP небольшой командой (AD-06), время отклика дашборда ≤ 3 с (AD-01), обработка до 1 млн записей (AD-02),
выделение логики KPI и отчётов (AD-05). Ограничение: развёртывание в облаке в Docker. Требуется сохранить возможность последующего
масштабирования.

## Решение
Выбран **слоистый монолит с элементами Clean Architecture**: четыре слоя (Presentation, Application, Domain,
Infrastructure), зависимости направлены к Domain, инфраструктура подключается через интерфейсы.
Приложение — один развёртываемый контейнер `bma-api`, модули (аутентификация, импорт, KPI, отчёты) разделены на уровне кода.

## Альтернативы
1. **Микросервисы** — плюсы: независимое масштабирование и развёртывание; минусы: избыточны для MVP и команды из 4 человек,
   высокая сложность инфраструктуры (сеть, наблюдаемость, распределённые транзакции).
2. **Монолит без слоёв** — плюсы: самый быстрый старт; минусы: бизнес-логика смешивается с доступом к данным,
   сложное сопровождение и тестирование, трудно выделять сервисы позже.
3. **Serverless** — плюсы: платите за использование; минусы: ограничения по времени выполнения для batch-импорта
   1 млн записей, привязка к провайдеру.

## Последствия
+ Быстрая разработка и развёртывание, один репозиторий и один пайплайн.
+ Чёткое разделение слоёв упрощает тестирование (бизнес-логика тестируется без БД) и параллельную работу участников.
+ Модули можно выделить в сервисы позже (прежде всего отчёты).
− Ограниченная горизонтальная масштабируемость: масштабируется приложение целиком.
− Необходимость рефакторинга при выделении сервисов; нужна дисциплина команды в соблюдении правил зависимостей между слоями.
