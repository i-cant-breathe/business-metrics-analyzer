# ADR-003. Выбор способа аутентификации (JWT vs сессии)

## Статус
Принято

## Контекст
В системе четыре роли (директор, менеджер, аналитик, администратор) с разными правами (AD-03).
Клиент — веб-интерфейс, взаимодействующий с REST API (FastAPI). Приложение должно оставаться stateless,
чтобы при необходимости запускать несколько реплик за Nginx. Требование безопасности: аутентификация по JWT, разграничение ролей.

## Решение
Использовать **JWT** (access-токен с коротким сроком жизни + refresh-токен). В токен включаются `sub`, `role` и `exp`;
подпись проверяется на каждом запросе зависимостью FastAPI, роль проверяется в слое Presentation.
Работа с токенами инкапсулирована в `JwtProvider` за интерфейсом `ITokenProvider`. Пароли хранятся как хэш (bcrypt/argon2).

## Альтернативы
1. **Серверные сессии (cookie + хранилище сессий)** — плюсы: легко отозвать сессию, нет данных в токене на клиенте;
   минусы: нужно общее хранилище сессий (Redis) для нескольких реплик, больше состояния на сервере, сложнее для не-браузерных клиентов API.
2. **OAuth2/OIDC через внешний провайдер (Keycloak)** — плюсы: готовые SSO и управление пользователями;
   минусы: лишний контейнер и сложность для MVP; можно перейти позже, заменив `JwtProvider`.

## Последствия
+ Stateless-API: проще масштабировать и разворачивать в Docker.
+ Роль доступна из токена без обращения к БД на каждый запрос.
+ Замена механизма локализована в `JwtProvider`.
− Отзыв токена до истечения срока сложен: нужны короткий TTL и (при необходимости) чёрный список в Redis.
− Секрет подписи нужно хранить в переменных окружения и ротировать; роль в токене устаревает до обновления токена.
