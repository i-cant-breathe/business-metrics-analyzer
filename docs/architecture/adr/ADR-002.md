# ADR-002. Выбор СУБД (PostgreSQL vs SQLite)

## Статус
Принято

## Контекст
Приложение хранит до 1 млн записей о продажах, пользователей, роли, метаданные отчётов и журнал аудита.
Дашборд должен отвечать за ≤ 3 с (AD-01), импорт идёт пакетами (AD-02), к БД одновременно обращаются
несколько пользователей и фоновая задача импорта. Развёртывание — в облаке в Docker.

## Решение
Использовать **PostgreSQL 16** в отдельном контейнере. Доступ — через SQLAlchemy (слой Repository),
миграции — через Alembic. Для разработки и автотестов допускается SQLite благодаря изоляции за репозиториями,
но продуктивная среда — только PostgreSQL.

## Альтернативы
1. **SQLite** — плюсы: ноль настройки, один файл; минусы: единственный писатель (блокировка при импорте во время работы
   пользователей), слабая конкурентность, нет полноценной клиент-серверной модели и ролей доступа, неудобно для нескольких реплик приложения.
2. **MySQL/MariaDB** — плюсы: распространённая, зрелая; минусы: у команды нет преимуществ перед PostgreSQL,
   у PostgreSQL богаче аналитика (оконные функции, `COPY` для быстрого bulk-импорта).
3. **Колоночная/OLAP-БД (ClickHouse)** — плюсы: очень быстрая аналитика; минусы: избыточна для 1 млн записей и MVP.

## Последствия
+ Надёжные транзакции (ACID) и конкурентный доступ — импорт не блокирует чтение дашборда.
+ Быстрый bulk-импорт (`COPY` / пакетные вставки) и индексы по периоду для KPI.
+ Бизнес-логика не знает о конкретной СУБД благодаря Repository и Unit of Work.
− Дополнительный контейнер и ресурсы (2 CPU, 2 GB), нужно настраивать резервное копирование.
− Различия диалектов SQLite и PostgreSQL в тестах: ключевые интеграционные тесты нужно гонять на PostgreSQL.
